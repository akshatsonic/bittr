## Problem Statement

Physical workplaces have no low-friction shared social layer that works without internet. Slack is async and internet-dependent. Group chats require everyone to be on the same platform. Bitter is a fun team timeline that lives entirely in the physical space — posts hop between phones over Bluetooth, no Wi-Fi, no internet, no server. Each team gets its own room. People post random stuff. The network is the building.

## What Makes This Cool

Two phones in the same office, airplane mode on both, and a post appears. No servers, no Wi-Fi, no accounts, no app store data requirements. The mesh is the infrastructure. Inspired by Jack Dorsey's BitChat, but shaped for the "fun office timeline" use case rather than censorship resistance. The Nostr event format means that if you ever get Wi-Fi, your offline posts can bridge to the global Nostr network without re-signing.

The "whoa" moment: someone locks their phone, walks to the other side of the office, and their post is already there — relayed by phones they never touched.

## Constraints

- **Platform:** Android first (Kotlin + Android Studio)
- **Team:** Solo builder, BLE is new territory
- **Use case:** Same physical workspace, close proximity (one floor, one building)
- **MVP scope:** One public room, no encryption, mesh working
- **Timeline:** 8-12 weeks (honest, given BLE learning curve)

## Premises

1. **Simultaneous Central + Peripheral works on your team's devices.** Android 5.0+ (API 21) supports advertising; modern Qualcomm-based Android phones (2020+) handle simultaneous scan+advertise reliably. Test early on your actual devices — budget phones with MediaTek chipsets may vary.

2. **Merkle tree root broadcast + GATT sync is the right MVP mechanism.** Each device maintains a Merkle tree over the current calendar day's posts (midnight-to-midnight local time). Leaves are SHA-256 hashes of individual Nostr event IDs, sorted lexicographically, combined bottom-up into a complete binary tree. The root hash (truncated to 20 bytes) is broadcast in every BLE advertising packet. If a neighbor's root hash differs, initiate a GATT connection; use the Merkle tree branch hashes to identify exactly which tweets are missing, then pull only those. No per-tweet managed flooding needed for MVP. Daily rollover = natural tree reset: yesterday's posts are kept in a read-only archive DB but not included in the active Merkle tree. Trade-off: 0-10 second message latency vs. implementation simplicity. For a fun office timeline, this is the right call.

3. **Foreground Service is non-negotiable.** Android kills background BLE scans. A persistent Foreground Service (with a system notification) is required from Day 1 for the mesh to keep running when users lock their phones. Without this, the app is a demo, not a tool.

4. **BLE on Android takes longer than expected.** Debugging is opaque (sparse logs, device-specific behavior, race conditions that only appear on real hardware). Plan for 2x the time on BLE-specific issues relative to any other Android feature.

5. **Public room = anyone in range can see the timeline.** Room is identified by a channel name/ID in the GATT packet. No keys. No encryption. This is the intended behavior for a fun, open office timeline.

## Approaches Considered

### Approach A: Merkle Tree Root Sync MVP (chosen)
Periodic Merkle root hash broadcast via BLE advertising at 250ms interval. Each device builds a Merkle tree over the current calendar day's posts. On root hash mismatch, GATT connection; exchange branch hashes to locate missing tweets, pull only the missing leaves. One public room. Basic timeline UI (post, read, scroll). Foreground Service for background operation.

Effort: L (8-12 weeks, BLE being new)
Risk: Medium — single propagation mechanism, smallest BLE surface area

Pros:
- One mechanism to learn and debug
- Root hash + GATT is the hardest architectural piece — learn it right, once
- Natural extension: add managed flooding later for lower latency, add rooms + encryption after
- Produces the real "whoa" moment

Cons:
- 0-10 second message delay (sync cycle latency)
- Foreground Service notification visible to users at all times
- BLE debugging will be painful on real devices

### Approach B: Mock Transport → BLE
Build full product (UI, data model, Nostr events, room logic) over local WiFi first. Get the team using it. Swap in BLE transport later.

Effort: M + L (12-15 weeks total)
Risk: Low for product, deferred for BLE

Pros: Usable in 5-7 weeks, debuggable over TCP, validates the product before the hard transport work
Cons: Delayed "whoa" moment, BLE phase may never arrive, two transports to maintain

### Approach C: Full Hybrid (managed flooding + root hash)
Both mechanisms as described in the original architecture doc: TTL-based flooding for live tweets + root hash + GATT for historical sync.

Effort: XL (16-20 weeks)
Risk: High — two propagation mechanisms, harder state machine, more to debug when BLE is new

## Recommended Approach

**Approach A.** Merkle tree over the current calendar day, root hash broadcast, GATT drill-down on mismatch. Single sync mechanism. Learn BLE once, right. The latency trade-off is invisible in an office setting. The 1-day tree scope makes worst-case sync trivially small and gives the timeline a natural "today" boundary that users intuitively understand. Flooding can be added later for lower latency; rooms and encryption come after that.

## Decisions Made

- **Nostr key management UX:** Auto-generate a Nostr keypair on first launch, store locally in Android Keystore. No onboarding screen — it just works.
- **Collision avoidance rule:** When two devices simultaneously detect a hash mismatch and both attempt to connect, the device with the lower 4-byte device ID (from the advertising packet, binary comparison) acts as GATT client (initiates connection); the other waits as GATT server. On the rare tie (same 4-byte ID), both attempt to connect; one receives GATT_ERROR and retries after 100ms random backoff.
- **Stop-and-wait clarification:** During a GATT session, the GATT client halts BLE scanning. The GATT server continues advertising (so other devices can discover it). Both resume full operation after disconnect.
- **Tweet character limit:** 280 chars max for MVP. Keeps GATT payload predictable.
- **Data retention:** Active Merkle tree covers the current calendar day only (midnight-to-midnight local time). At day rollover, the tree resets; yesterday's posts move to a read-only archive table in SQLite, not included in future sync. The "timeline" shows today's posts; yesterday is accessible via scroll/archive but does not affect sync performance.
- **Re-join / heal:** Because the tree is bounded to one calendar day, the worst case is syncing an entire day's posts from scratch. For an office timeline, that's realistically 20-100 tweets — trivially small. No delta cap needed for MVP.

## Open Questions

1. **Android minimum API level?** API 21 (Android 5.0) covers 99%+ of devices, but extended advertising (larger payload) requires API 26 (Android 8.0). What's the oldest device on your team?
2. **Room discovery mechanism?** For MVP (one public room), the channel name can be hardcoded or set at app launch. No discovery needed. Plan for named rooms in v2.
3. **Nostr format vs. simpler internal format?** Nostr event format (public key + signature + timestamp) adds a crypto library dependency and signature verification to the MVP. Decision needed: carry the full Nostr structure now (correct for Nostr bridge future) or use a simpler internal event format and migrate later. Recommendation: use Nostr format now — the crypto overhead is small (secp256k1 library, ~30KB) and migration debt is worse.

## Next Steps

**Week 1-2: Android BLE fundamentals**
- Build a minimal "hello world" BLE app: advertise a UUID, scan for it on another device, log discovery
- Read Android BLE best practices docs (especially BluetoothLeScanner, BluetoothLeAdvertiser, BluetoothGattServer, BluetoothGattCallback)
- Set up the Foreground Service shell early — get the notification showing

**Week 3-4: Merkle tree + root hash broadcast**
- Define the data model: Nostr event structure (public key 32B, timestamp 8B, content up to 280 chars, secp256k1 signature 64B). **Generate the Nostr keypair now** (Week 3), store in Android Keystore. The Week 11 "identity setup" step only adds the nickname UI — the keypair already exists and signs posts from Day 1.
- Implement SQLite/Room database with two tables: `posts_today` (current calendar day, active for sync) and `posts_archive` (previous days, read-only). Day rollover at local midnight moves `posts_today` rows to `posts_archive` and resets the Merkle tree.
- Implement Merkle tree over `posts_today`:
  - Leaves: `SHA-256(nostr_event_id)` for each post, sorted lexicographically
  - Complete binary tree: if leaf count is odd, duplicate the last leaf as a sibling
  - Internal nodes: `SHA-256(left_child_hash || right_child_hash)`
  - Rebuild the full tree on each new post; for an office timeline (≤100 posts/day), this is cheap
  - Root hash truncated to 20 bytes for BLE advertising
- BLE advertising packet layout: `[2B company ID: 0xFFFF][1B version: 0x01][1B room ID][4B device ID][20B Merkle root, truncated]` = 28 bytes. Device ID is a random 4-byte value generated at first launch and stored locally.
- The full Nostr public key is exposed via a GATT `IDENTITY` read characteristic for signature verification during sync.
- Advertise every 250ms; tune based on real-device latency measurements.
- **Power note:** Continuous scan + advertise at 250ms raises battery drain ~10-15% in background. Surface this in the Foreground Service notification ("Bitter is running — uses Bluetooth").

**Week 5-6: GATT sync with Merkle tree comparison**
- GATT protocol: one service UUID, three characteristics:
  - `MERKLE_QUERY` (write + notify): client writes branch-level hashes; server responds with which branches differ and their children hashes. Used to drill down the tree.
  - `TWEET_FETCH` (notify): server streams missing tweet payloads once delta is identified.
  - `IDENTITY` (read): server exposes full 32-byte Nostr public key for signature verification.
- Negotiate MTU to 512 bytes (`requestMtu(512)`) before any data exchange. All payloads use `[4B length][payload bytes]` framing.
- **Merkle sync protocol (level-by-level):**
  1. Client detects root hash mismatch → connects
  2. Client writes its branch hashes at depth 1 (left and right subtree hashes) to `MERKLE_QUERY`
  3. Server compares, responds with which subtrees differ and their depth-2 children hashes
  4. Client continues drilling down differing subtrees until leaves (individual tweet IDs) are identified — typically 3-5 rounds for a 100-tweet day-tree (depth ~7)
  5. Once missing tweet IDs are known, server streams them via `TWEET_FETCH` notifications
  6. `TWEET_FETCH` payload per notification: Nostr event JSON (UTF-8), `[4B length][JSON bytes]`; one tweet per notification
- **Why Merkle beats flat ID list:** For a day with 100 tweets and 10 missing, the flat approach sends 100 × 32B = 3.2KB of IDs to find 10. Merkle finds the same 10 missing tweets in ~5 rounds of branch hashes (~160 bytes total exchanged before streaming the actual tweets). More efficient as day-tweet count grows.
- `MERKLE_QUERY` write format: `[1B depth][1B branch_index][32B hash]` per branch; batch multiple branches in one write up to 512B MTU.
- **Collision avoidance:** Device with lower 4-byte device ID (from advertising packet) acts as GATT client. On tie (same ID), both attempt to connect; one receives GATT_ERROR and retries after 100ms random backoff.
- Stop-and-wait: GATT client pauses scanning during session; GATT server continues advertising; both resume after disconnect.
- No delta cap needed — worst case for a 1-day tree is ~100 tweets, which fits in a handful of `TWEET_FETCH` notifications.
